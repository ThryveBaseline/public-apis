# Ironbeam execution review — October 21, 2026

**Three implementation gaps fixed; actual broker qualification remains blocked by pending credentials. Live orders remain disabled.** The review covered official API documentation, firsthand developer/trader forum reports, and a public GitHub client maintainer's notes. Reports below are evidence of a risk to test, not proof that every current account has the same broker defect. No additional substantiated API shutdown incident was found in this bounded search; absence of a report proves nothing about reliability.

| Problem and source | Does our code protect us? | Actual demo evidence still required / missing fix |
|---|---|---|
| **Parent bracket updates can remove protection or unexpectedly execute entry.** A developer reported HTTP 200 cancelling children on an unfilled entry, then an unexpected entry/orphan position. Staff explicitly say to update the **child** order ID. [Forum, Apr–Jun 2026](https://www.ironbeam.com/community/t/order-update-for-bracket-order/979) | **Critical defect fixed.** Our filled-position alignment and breakeven previously updated the parent. They now amend only verified active STOP/LIMIT children, preserve quantity, and verify both legs after each change. Uncertain amendments are journaled before transmission and never blindly repeated after restart. | **Required, first priority:** MARKET and STOP entries, long/short; filled and partially filled entries; move stop, confirm sibling target and remaining quantities; timeout before/after acceptance; prove stop still executes. Do not amend inactive children or fall back to parent updates. The reported pending-LIMIT case is not identical to our filled-position case. |
| **WS order status stays `st:0`/NEW after modifications, cancellations and fills.** Two developers report it; no visible resolution. [Forum, Apr–May 2026](https://www.ironbeam.com/community/t/websocket-v2-stream-order-lifecycle-updates-modify-cancel-state-changes-all-arrive-with-st-0/976) | **Already defended:** WS account events trigger REST reconciliation; fills are deduplicated and positions checked. WS status never establishes a fill or working protection. | **Required:** capture WS, REST and portal views for the same order IDs through fill, cancel and amendment. Measure REST convergence; our sequential snapshots are not atomic. |
| **Bracket placement payload ambiguity.** One developer's absolute-price LIMIT bracket produced only the entry; another reports working offsets. [Forum, Mar 2026](https://www.ironbeam.com/community/t/need-help-on-bracket-order-placement-via-api/926). The downloadable `OrderRequest` description calls offsets unsupported while endpoint prose/examples describe them. [API v2.1](https://docs.ironbeamapi.com/) | **Partial protection:** actual exposure must have accepted, correctly sized children; missing protection triggers halt/emergency demo close. Absolute fields remain a **provisional**, unqualified contract. | **Required:** verify exact MARKET/STOP payloads, GTC encoding, offset units/reference and resulting child prices on both sides. Only use an alternative payload after observed acceptance and protection. A stop added after an unprotected fill is not an acceptable substitute for native protection. |
| **429 and request storms.** Staff confirm **10 requests/sec**. [Forum, May 2026](https://www.ironbeam.com/community/t/429-rate-limiting/1024). A client maintainer reports longer cooldowns and repeated 429s prolonging failures. [GitHub maintainer notes](https://github.com/wboayue/ironbeam-rs/blob/main/CLAUDE.md) | **Defect fixed:** all calls on the client, including auth/subscription/recovery, are spaced by 250ms; balance notifications are coalesced. HTTP 429 starts at least a 30-second local cooldown, honoring longer `Retry-After`. No queued mutation/retry; entry freshness/cutoff is rechecked after pacing. | **Required:** paced normal load plus a broker-approved throttle exercise; recovery/exit latency under throttling. The 30-second policy is conservative, not a broker guarantee. Other programs sharing credentials can consume the same allowance. |
| **Account events are asynchronous; balances can update on price changes.** Staff confirm event sequence follows actual events and balances are independent. [Forum, Feb 2026](https://www.ironbeam.com/community/t/about-a-sequence-of-ws-messages/909) | **Related defect fixed:** a cash mismatch formerly prevented inspection of a missing stop. Protection now takes priority; cash discrepancies still block readiness. Rate protection also prevents a REST snapshot for every balance tick. | **Required:** actual fee/balance timing, partial fills and mixed snapshots. Inconsistent exposure still halts; do not infer a consistent position from mixed reads. |
| **Subscription errors can coexist with active/sticky indicator streams; reconnect order matters.** Firsthand reports describe HTTP 400 while indicators continue. [Forum, 2025–26](https://www.ironbeam.com/community/t/subscribing-and-unsubscribing-from-indicators/784) | **Mostly avoided:** we consume raw trades/quotes, open WS before subscribing, create a new stream ID after disconnect, reject gaps/revisions and deduplicate identical trades. We do not use indicator subscriptions. | **Required:** failed/duplicate subscribe, reconnect, old-stream leakage and fresh-data confirmation. Missing context is still a routing blocker; automatic arbitrary-gap backfill remains incomplete. |
| **Working orders consume margin and can obstruct exits.** Staff explain worst-case exposure includes orders; traders describe margin violations during closing attempts. [Forum, 2023](https://www.ironbeam.com/community/t/order-group-margin-violation-message-trying-to-place-an-order/60) | **Partial:** pending risk/margin is reserved, broker availability checked, and cancellation confirmed before calculating close quantity. | **Required:** native OCO margin treatment, cancellation/fill races, partial exits and rejected close. **Unresolved critical operational gap:** cancel-then-close is not atomic; losing connectivity after cancellation can leave exposure without a stop. No documented reduce-only/atomic flatten guarantee has been established. Independent broker recovery must be exercised. |
| **Completed candles and live quotes have different timing.** Staff confirm TradeBars/TimeBars are completed bars; quotes support forming candles. [Forum, Oct 8, 2026](https://www.ironbeam.com/community/t/best-way-to-render-a-live-forming-candle-tradebars-timebars-only-push-on-close/1110) | **Partial:** JJ receives completed minutes from raw trades; stale data and gaps block routing. Exchange-time/sequence semantics are still unqualified. | **Required:** confirm `st` send time versus exchange trade time, final-minute completeness and latency. Delayed demo can qualify mechanics only. |
| **GB10 disappears / stops survive but local cutoff logic cannot run.** Ironbeam states platform orders are server-side. [Official support](https://www.ironbeam.com/knowledge-base/does-the-ironbeam-platform-support-server-side-order-management/). Day margin ends in the final 15 minutes before market close and can change. [Official margins](https://www.ironbeam.com/margins/) | **Still unproven:** native GTC children, durable ledger and recovery exist. None proves our exact API bracket persists after amendment, or that cutoff liquidation happens while GB10 is down. | **Required, first priority:** interrupt only the demo process/network; independently observe surviving stop, execution and sibling cancellation; restart with no duplicate. Confirm account-specific cutoff/holidays and an independent liquidation route. Current published MNQ overnight margin exceeds the configured account allocation; do not rely on forced broker liquidation. Keep paper services running. |

The GitHub notes also report response-field/type differences and empty security-definition batches when one symbol is invalid. Our startup validation blocks missing definitions and never silently rolls contracts. Confirm real response shapes in the read-only probe; no parser workaround was invented. The reviewed GitHub repository returned no issues in the connected issue search; its maintainer notes are firsthand implementation observations, not broker promises.

The corrected mock now reproduces destructive parent updates instead of assuming they preserve protection. Ten focused regression cases plus strengthened existing amendment tests pass; **124 tests total**. Evidence covers lost sibling orders despite successful HTTP responses, accepted/unaccepted amendment timeouts across restart, changed partial fills after breakeven, protection hidden by cash lag, request pacing/cooldown, stale WS status and entry expiry during pacing. These remain synthetic tests. Frozen JJ V1 and paper code were not changed; no historical backtest or optimization was run.
